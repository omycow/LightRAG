# SG 증거 레이어(L1/L2/L3)와 퀄리티 체크 — 동작 명세 (v5.20/v5.21 기준)

> 코드 기준: `structure_graph.py`, `quality.py`, `retriever.py`, `evolver.py`.
> 모든 수치는 코드의 실제 값. 벤치마크 정답은 어느 단계에도 입력되지 않는다.

## 1. 구조그래프 엣지의 3층 증거

한 문서쌍(A||B)의 엣지는 레이어별로 독립 기록되고, 탐색 시 **유효가중 = max(레이어 w × 레이어 계수)**로 합산된다.

| 레이어 | 계수 | 생성 주체 | 갱신 |
|---|---|---|---|
| L1 `explicit_ref` | 1.0 | 결정적 스캐너 (인제스트 시 1회) | 불변 |
| L3 `llm_curated` | 0.8 | 백그라운드 LLM (evolver) | 감쇠 대상 |
| L2 `co_retrieval` | 0.6 | 룰 (매 쿼리 인라인) | 강화/감쇠 |

### L1 — 명시적 참조 (문서가 스스로 선언한 링크)
- **입력**: 인제스트된 청크 텍스트 전체 (`kv_store_text_chunks.json`)
- **추출 규칙 (정규식 2종, 코퍼스 컨벤션 하드코딩 없음)**:
  1. 파일명 리터럴 언급 — 확장자 목록은 코퍼스에서 자동 수집: `[\w\-\.]+\.(html|md|docx|…)`
  2. 제너릭 ID 토큰 `[A-Z][A-Z0-9]{1,7}(-[A-Z0-9]{2,8}){1,3}` (예: AUR-940, SPEC-FW-0001)
     → "파일명에 그 ID가 든 파일"을 소유자로 해석 (소유자 복수면 최대 3개 전부 연결)
- **가중치**: `w = min(1.0, 0.5 + 0.1 × 언급횟수)` — 1회 언급 0.6, 5회+ 1.0
- **본 코퍼스 실측**: 1,719 엣지, ValB 정답쌍 89/90 커버
- **사용처**: 확장(EXPAND) 이웃 — L1은 정렬에서 무조건 학습 레이어보다 우선.
  에스코트(1위 문서의 최강 L1 이웃을 랭크 2에) 1순위 소스. D8 원칙: L1에 어휘 신호 곱하기 금지

### L2 — 공동검색 통계 (쿼리들이 만든 상관 증거)
- **입력**: 매 쿼리 응답 후, 관찰 창의 문서들 (v5.20: 상위 10 / v5.21: 관찰 16)
- **게이트 2중**:
  1. 퀄리티 게이트 — 그 쿼리의 셀프 점수가 최근 분포 p60(자가보정) 이상일 때만 학습
  2. **선택적 에코(v5.8 핵심)** — 우리 확장이 주입한 문서가 낀 쌍은 **그 쌍에 L1이 있을 때만** 강화
     (문서가 선언한 링크의 "사용 증거"는 정당, 무근거 쌍 생성은 에코 챔버 → 금지)
- **강화**: 쌍마다 `w += 0.1` (cap 1.0), count 증가
- **감쇠**: evolver 사이클마다, 직전 사이클에 탐색에 안 쓰인 엣지 `w ×= 0.95`, 0.15 미만이면 레이어 삭제
- **역할**: 크로스레퍼런스 없는 코퍼스에서의 일반 경로 — 단, ablation 실측으로
  "검색이 같이 띄운 적 있는 쌍"만 배울 수 있다는 도달 한계 확인 (DESIGN_HISTORY 2026-07-14)

### L3 — LLM 큐레이션 (의미 관계, 위키처럼 축적)
- **입력**: evolver 사이클에서, 고품질 쿼리들이 2회+ 공동검색했는데 L1/L3가 없는 문서쌍 후보
- **절차**: 두 문서의 대표 청크 발췌 + 그 쌍을 띄운 실제 쿼리들 → LLM에게
  `spec-of|implements|tests|references|part-of|none` + confidence + 근거문장 요구
  → `none` 아니고 confidence ≥ 0.6일 때만 엣지 생성 (`w = 0.5 + conf×0.4`, cap 0.9)
- **증거 강제**: 엣지에 근거 청크 ID 저장, evolution_log에 rationale 기록
- **예산**: 사이클당 LLM 총 50콜 안에서 (섀도 플래너와 공유), 감쇠 대상
- 같은 예산에서 **문서 프로필**(자주 검색되는 문서의 2문장 요약 → SG 노드에 저장, 스코프 라우팅용)도 생성

## 2. 퀄리티 체크 (`quality.py` — LLM 없음, 매 쿼리 ~1ms)

응답 직후 5신호를 가중 합산해 0~1 점수. **정답 아닌, "잘된 검색의 통계적 징후"만 측정**:

| 신호 | 가중 | 계산 |
|---|---|---|
| sim_strength | 0.25 | 벡터 top-k 코사인을 [0.3,0.8]→[0,1] 리스케일, top1과 mean@k 평균 (QPP의 NQC/WIG 계열) |
| fusion_agree | 0.20 | BM25 top-k와 벡터 top-k의 **문서 단위** overlap coefficient (독립 랭커 합의) |
| term_coverage | 0.25 | 쿼리 핵심 텀(한국어 조사 제거, 스템 프리픽스 관용)이 상위 5청크에 존재하는 비율 |
| struct_coverage | 0.20 | 상위 5 base 문서 중 "자기 강한 L1 이웃(w≥0.5)이 base top-20에 동반된" 비율 — co-retrieval 프록시 |
| scope_align | 0.10 | 상위 문서가 SG 스코프 예측 안에 든 비율 |

- 결측 신호는 가중 재정규화. 산출 후 러닝 윈도(최근 200쿼리) 분포에 적재
- **게이트는 절대값이 아니라 퍼센타일 (자가보정, 코퍼스 무관)**:
  - `p70+` → 플랜캐시 승격 ("이 질문 유형은 이 플랜으로")
  - `p60+` → L2 강화 허용
  - `p30-` → 주의 목록 → 백그라운드 섀도 플래너의 LLM 재분석 대상
- **한계 명시**: 프록시라서 속을 수 있음 (실례: v5.12 타입프라이어) — 그래서 최종 심판은
  항상 동결+무개입 벤치마크 런 (그라운드룰 7 / P1)

## 3. 학습 루프에서의 결합 (한 쿼리의 생애)

```
응답(핫패스, LLM 0) → 퀄리티 5신호 채점
  ├─ p70+ : 플랜 캐시 승격 + 모드 성적(골격 키) 갱신
  ├─ p60+ : L2 강화 (선택적 에코 규칙 하)
  ├─ p30- : 분석 큐 → [백그라운드] 섀도 플래너가 LLM 플랜 시운전 → 이기면 캐시 교체
  └─ (v5.20) 캐시 응답인데 p60 미만 → 재최적화 큐
[evolver 사이클] L2 감쇠 / L3 후보 LLM 판정 / 문서 프로필 / Track K 위생(가드+롤백)
```
